# Piniaストア状態管理詳細設計

Vue / Piniaの現行実装を調査し、画面操作ごとのストア変更と関連APIを、短い表記の５列表に整理する。アプリケーションコードは変更しない。既存仕様や一般的な実装から動作を推測せず、実装で確認できた事実と未確認事項を区別する。

## 1. 対象と出力先

1. 指定されたプロジェクト・画面・ストアを対象とする。指定がなければプロジェクト全体のPiniaストアと画面を対象とする。対象外の状態（画面ローカル、Cookie、サーバー状態など）は本文に明記する。
2. 対象プロジェクトの文書配置・命名・更新規則を確認する。出力先の指定があればそれに従い、なければ既存の詳細設計の配置に合わせる。適切な既存の配置がなければ `docs/store-state-management.md` とする。既存の関連資料は内容を確認して更新し、無関係な文書は上書きしない。文書一覧やリンクの同時更新がプロジェクトで必要な場合は合わせて行う。
3. レポートの対象範囲、調査した実装、静的調査か実行検証済みかを明記する。実行していない動作は実行検証済みと書かない。

## 2. 実装を追跡する

対象内の全画面・ストアを列挙し、それぞれ次の経路を最後まで追う。全画面の初期表示を確認し、何も変更しない画面も一覧に含める。

- **ストア**：`defineStore`、Setup / Options Store、state、getter、action、初期値、reset / clear、直接代入、他ストアへの連鎖を確認する。永続化プラグイン、ブラウザー保存領域との同期・復元があれば、それらを含めて保持と破棄の範囲を確認する。
- **画面・共通処理**：ルーター、ガード、共通レイアウト、画面、子コンポーネント、composable、watch、ライフサイクルをたどる。ボタン、フォーム、タブ、画面初期表示、パラメーター変更、画面離脱、ログイン・ログアウトなど、実際に存在する起点に紐付ける。
- **非同期・API**：画面やストアからAPIクライアント、共通インターセプターまでたどり、HTTPメソッドと実際のパス、条件付きの呼び出しや後続APIを確認する。ストア自体のAPIと、同じ画面操作内で別の処理が呼ぶAPIを区別する。
- **分岐**：成功・失敗・キャンセル・認証切れ、入力検証、キャッシュ、同時要求、破棄後の応答、画面離脱・再表示を確認する。各分岐の対象と発生条件を特定し、特定の画面だけの例外を共通仕様として扱わない。
- **その他の起点**：タイマー、ブラウザーイベント、WebSocketなど、画面操作以外にストアを変更する起点があれば漏らさず別途記載する。

共通コンポーネントやストア間の呼び出しは実際の利用元までたどり、画面への波及を確認する。動的な参照などで追跡できなかった経路は「不明」とし、確認できた範囲と理由を残す。全画面・全ストア・共通処理を確認し、各イベントから変更先とAPIまで追跡または未確認箇所を明示できたら次に進む。

## 3. 資料を作成する

次の構成を基本とし、対象プロジェクトの実装に応じて項目を増減する。

### 対象と読み方

- ストア一覧：ストア名、PiniaのID、主な保持値。名前が実装にない場合は識別しやすい名称を付け、実際のIDを併記する。
- 表の用語：**設定**（データ・IDなどの保存）、**更新**（保持値の変更）、**クリア**（保持値の破棄・初期化）、**なし**（変更またはAPI呼び出しがない）を定義する。値の設定と更新が厳密に区別できない場合は、実装を反映した一貫した分類を使用する。
- 対応API列は画面操作に関連して呼ばれるAPIであり、必ずしもストア自身による呼び出しではないと明記する。共通操作を分ける場合は、画面別の「なし」には共通操作を含まないことを明記する。

### 画面操作とストア

共通操作と画面別操作を必要に応じて分け、同じ５列を使用する。

| 画面 | イベント | ストア | 処理概要 | 対応API |
|---|---|---|---|---|
| 商品詳細 | 初期表示 | 商品（`product`） | 設定（成功時） | `GET /api/products/{id}` |
| 商品詳細 | 画面離脱 | 商品（`product`） | クリア | なし |

上の行は形式例であり、対象プロジェクトで実際に確認した内容に置き換える。

- 画面は画面名、イベントは「初期表示」「検索ボタン押下」「タブ押下」「画面離脱」のような操作・ライフサイクルの粒度とする。ハンドラ名や内部実装のステップをイベント名にしない。
- 原則１行１ストアとし、１操作で複数ストアが変わる場合は行を分ける。ストア名とIDを併記する。変更のない初期表示も記載し、ストア参照のみなら該当ストアと「なし」、関係するストアがなければストア列も「なし」とする。
- APIは `GET /path/{id}` の形式で列挙する。取得条件がある場合や操作途中で複数APIを呼ぶ場合も実際の経路を示す。APIを呼ばない場合は「なし」、調査で特定できない場合は「不明」とする。
- 処理概要は設定・更新・クリア・なしを組み合わせ、必要なときだけ「（成功時）」「（失敗時）」「（取得時）」など短い条件を付ける。ストアの変更が条件付きの場合は、無条件の変更に見えないようにする。表のセルは単語か短文に統一し、長い説明は表の外に置く。
- 共通ガードや共通ヘッダーによる処理は共通操作に集約し、適用範囲と画面別操作との関係を明記する。同じ操作の共通処理を各画面に重複させない。画面固有の例外は省略しない。
- 行の対象は初期表示と、Pinia変更または関連APIがある操作を基本とする。参照のみの操作は必要に応じて「なし」とし、表に載せない操作の扱いと対象範囲を明記する。非画面起点は共通処理または別の短い一覧で示す。

### 表に収まらない情報

５列では正確に表せない場合に限り、対象の画面・イベント・ストアを特定して短く補足する。例えば変更される値、更新の順序とタイミング、条件ごとのAPI、キャッシュの有無、状態の種類、失敗時や破棄後の応答の扱い、永続化先、条件から外れる例外を記載する。実装にない共通ルールを作らず、表現できなかった点を明示する。

### 実装参照・調査の限界

対象の主要なストア・ルーター・共通処理・画面・APIの実装へのリンクをまとめる。各イベントや例外から根拠を特定できるよう、必要に応じて画面単位または補足単位で参照先を示す。動的な経路、条件、実行未検証などの限界は具体的に記載する。

## 4. 確認

- 実装上の全対象画面に初期表示行があり、関連操作・共通処理・画面以外の更新起点に漏れがない。
- 複数ストアへの連鎖、設定・更新・クリアの条件、APIのメソッド・パス・呼び出し条件が実装と一致する。参照のみ、変更なし、未確認を区別する。
- 各操作表のヘッダーと列数が５列で、１行１ストア、表記が短く統一されている。条件・順序や例外が曖昧な行には表外の補足がある。
- リンク先と文書配置規則を確認し、静的調査と実行検証を混同していない。

完成後、出力先、対象範囲、表に収まらなかった主な条件、未確認事項を簡潔に報告する。
