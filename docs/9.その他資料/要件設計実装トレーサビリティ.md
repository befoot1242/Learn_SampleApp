# 要件・設計・実装トレーサビリティ

## 1. 対象と判定基準

要件案、基本設計、詳細設計、現行ソースを機能・品質観点ごとに照合した結果を示す。要件案は確定仕様とはみなさず、要件との差分、未記載、実装未確認を区別する。本資料は文書とソースの対応を評価するもので、実装の正しさやテスト済みであることを保証しない。

照合日: 2026-10-31

| 判定 | 意味 |
|---|---|
| 追跡可能 | 各工程の記載・実装を相互に確認できる |
| 部分／差分 | 主要な対応はあるが、記載漏れ、未確定事項、または仕様差がある |
| 欠落 | 上位の記載が下位に展開されていない、または実装・詳細設計にある事項が上位に記載されていない |
| 不一致 | 詳細設計の記載とソースの動作が一致しない |

要件資料に一意な要件IDがないため、本資料では要件案の節・内容を照合単位とする。

## 3. 上位から下位への不足観点

### 3.1 要件から基本設計

| 要件案の観点 | 下位資料での確認 | 不足・差分 |
|---|---|---|
| OAuth2 Authorization Code + PKCE | 基本設計§6、§9はセッション認証への変更を記録 | 実装差分は明示されているが、要件案自体はOAuth2要件のまま。変更を承認済み差分として要件台帳に反映した記録は設計資料内で確認できない（リポジトリのCLAUDE.mdにはユーザ確認済みとの記載あり） |
| 取引登録タイムアウト後の状態照会 | 基本設計§4.3は取引一覧で状態確認を促す扱い | 個別の状態照会導線/APIではなく、一覧への誘導に置換。仕様差分として扱い、代替が要件を満たすか確定が必要 |
| 外部API障害時の縮退運転 | 基本設計§4.3にGET再試行・POST非再試行、§8に一部障害時挙動 | 利用可能機能、縮退条件、復旧条件、利用者への影響など「縮退運転」の全体仕様がない |
| 一覧2秒以内（95パーセンタイル） | 基本設計§8は実装・設定で保証を確認できないと記載 | 負荷条件、測定方法、目標達成の設計・検証記録が基本設計以降に展開されていない |
| CSRF/XSS/SQLi対策 | 基本設計§6はCSRF等を記載 | CSRF以外のXSS/SQLi対策について、具体的な設計観点・検証条件・結果への対応付けが不足 |
| 各種申請・入力フォーム | 要件案に画面・機能の記載なし | 基本設計F-09/S-08およびS-07は要件根拠を持たない。追加要件として位置付けるか、要件案の対象外サンプルと明記する必要がある |

### 3.2 基本設計から詳細設計

| 基本設計の観点 | 詳細設計での確認 | 不足・差分 |
|---|---|---|
| F-09/S-08 各種申請 | D-API §5、D-DB §6–7、S-08に入力/API/保存仕様あり | D-FLOWは対象をログイン・ユーザ管理・取引に限定しており、申請登録の処理フローがない。D-TXとAPIトランザクション一覧にも `POST /api/applications` がない。`ApplicationService.create()` の業務TXと監査 `REQUIRES_NEW` の関係が未設計 |
| データ設計概要 | 基本設計§5はユーザ、ロール履歴、監査ログ、取引のみ | 詳細設計D-DB §6にある `application_request` と `application_request_language` が基本設計の論理データ一覧にない |
| 監査対象 | 基本設計§7は認証・ユーザ操作・取引登録を記載 | 詳細設計D-API §5/D-DB §7と実装にある `APPLICATION_CREATE` が基本設計の監査対象一覧にない |
| APIトランザクション全体 | D-TX §3、D-TX-MATRIX §3はAPI単位の一覧を掲げる | 一覧の対象から申請APIが漏れている。特にD-TX-MATRIXは全HTTP APIを対象と記載しているため、対象範囲の説明と内容が不一致 |

### 3.3 詳細設計から実装

| 詳細設計 | 実装確認 | 判定 |
|---|---|---|
| D-API §3.1はログイン要求の `username` / `password` をNotBlankとし、Bean Validationエラーを400と記載 | `AuthController.login` の `LoginRequest` 引数は `@Valid` で検証し、共通例外ハンドラが400 `VALIDATION_ERROR` と `fieldErrors` を返す。D-TX-MATRIX §4にも記載 | **追跡可能**。詳細設計の検証仕様と実装が一致する |

## 5. 優先して解消すべきトレース断点

1. 各種申請と入力フォームを正式な要件、または「要件対象外の学習用追加機能」のどちらとして扱うか決め、要件→基本→詳細の根拠を揃える。
2. 申請機能を残す場合、基本設計のデータ/監査概要と詳細設計の監査action一覧を更新し、D-FLOW、D-TX、D-TX-MATRIXへ申請処理・トランザクションを追加する。
3. ログイン要求のNotBlank検証を実装するか、API詳細設計上の検証仕様を実装に合わせる。
4. 縮退運転、性能目標、XSS/SQLi対策の要件を、判定可能な設計・検証条件まで具体化する。
5. OAuth2方式と登録後の状態照会導線は、記録済み差分が正式に承認済みかを設計上も明確にする。

## 7. 実装課題一覧

| ID | 課題 | 内容 | 状態 |
|---|---|---|---|
| I-01 | ログイン入力検証 | `AuthController.login` で`LoginRequest`を`@Valid`検証し、空文字・nullを400 `VALIDATION_ERROR`として返す | 解消 |
| I-02 | 監査とcommitの不整合 | ユーザ操作・申請登録は成功監査イベントを業務TX内で発行し、commit後に独立TXで記録する | 解消 |
| I-03 | 申請の失敗監査 | 入力検証（400）と業務検証（409）を、入力値を含めず理由コードのみで`APPLICATION_CREATE`失敗監査として記録する | 解消 |
| I-04 | 縮退運転・性能・XSS/SQLi | 要件案にあるが実装・検証がない | 未対応 |
| I-05 | 状態照会導線 | 取引登録タイムアウト後の状態照会APIがない（一覧誘導のみ） | 未対応 |
| I-06 | H2コンソール | 既定で無効とし、`dev`プロファイルでのみ公開・CSRF除外・同一オリジンframe許可を適用する | 解消 |
| I-07 | CSRF失敗応答 | CSRFトークン不正・欠落時は403 `CSRF_INVALID` を返し、画面再読み込みと再試行を案内する | 解消 |
| I-08 | 申請の選択値検証 | 性別・都道府県・連絡方法等の許容値検証が`@Size`等に留まる可能性（未精査） | 未対応 |
